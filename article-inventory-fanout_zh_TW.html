我在 MySQL driver 的門口站了八分鐘，然後看到一次「改個數量」寫了三張表

2026-07-26 8 分鐘窗口 / 4,341 條語句 inventory-example + MySQL 8.0

前幾天我又做了一件平常不太會做的事：不改任何一行 code，對一個正在跑的庫存管理服務（Gin + GORM + MySQL）掛了幾個觀測點，然後坐著看八分鐘。

八分鐘裡，我看到一件到現在還讓我有點在意的事——前端只是改了某個商品的數量，資料庫這邊卻收到六條語句，其中兩條是往 categories 和 suppliers 這兩張「我根本沒打算動」的表寫 INSERT。

這篇聊的不是工具，是「站在對的位置，把一個 CRUD 服務底下真正發生的事看完」這件事本身。

先決定要站在哪裡看

這個服務是最典型的三層：Gin handler → service → repository → GORM → MySQL。你寫的是 db.Save(product)，真正送到 MySQL 的是什麼，中間隔了兩層。

我第一次選的位置是 GORM 內部的收斂點 gorm.(*processor).Execute——上次觀測另一個服務時就是站在那裡。模板照抄：SQL={string(stmt.SQL.buf)}。

結果面板上抓到的是這個：

SQL=len=67 | rows=6
SQL=len=63 | rows=5

stmt.SQL 是個 strings.Builder，它的內部 buffer 沒被展開成字串，我只拿到長度。這次的 GORM 版本、這次的建置條件下，這條路走不通。

所以我往下退了一層，退到驅動的門口：

func (mc *mysqlConn) QueryContext(
        ctx context.Context, query string, args []driver.NamedValue) (driver.Rows, error)

func (mc *mysqlConn) ExecContext(
        ctx context.Context, query string, args []driver.NamedValue) (driver.Result, error)

query 在這裡是一個實實在在的 string 參數——它就是即將送上線的那條 SQL。讀走 QueryContext、寫走 ExecContext，兩個點就把整個服務對資料庫做的每一件事切成乾淨的兩半。

於是這一輪的觀測設定是這樣：

  • 讀（connection.go:510）：Q={query}
  • 寫（connection.go:529）：Q={query}
  • 另外在應用自己那一層放三個純計數：ProductRepository.FindAll、ProductRepository.Create、StatRepository.GetStats——用來跟底下的 SQL 對帳。

上層數「一次 API 呼叫」，底層數「幾條 SQL」。這兩個數字之間的比例，等一下就是整篇的主角。

前四分鐘：沒有人在看的服務

第一段窗口（2026-07-25 16:19:31Z → 16:23:31Z）我什麼都沒做，只有服務內建的 demo 模擬器每兩秒動一次：抓一次商品清單，然後隨機做新增／修改／刪除。四分鐘，底下跑了 1,203 條 SQL（讀 800、寫 403）。

去重之後長這樣（逐字抄自面板）：

我寫的 Go面板上真正送到 MySQL 的次數
repo.FindAll("") 的第一趟SELECT * FROM `products`121
（同一行 Preload("Category")）SELECT * FROM `categories` WHERE `categories`.`id` IN (?,?,?,?,?,?)121
（同一行 Preload("Supplier")）SELECT * FROM `suppliers` WHERE `suppliers`.`id` IN (?,?,?,?,?)121
db.Create(product)INSERT INTO `products` (`name`,…,`created_at`,`updated_at`) VALUES (?,?,?,?,?,?,?,?)114
db.Delete(&Product{}, id)DELETE FROM `products` WHERE `products`.`id` = ?91

第一件對得上的事：FindAll 那個純計數，四分鐘剛好也是 121 次——而面板上 SELECT * FROM `products` 也是 121。上層一次呼叫，底層一條主查詢，一分不差。同樣的，Create 計數 114 對上 INSERT INTO products 114。兩層之間對得起來，後面所有推論才站得住。

第二件事我本來以為會看到、結果沒看到：N+1。一次 Preload 兩張關聯表，我等著看它對每一列商品各發一條 SELECT，結果面板上是兩條 IN (?,?,…) 的批次查詢。GORM 幫你收好了——所以一次列表查詢是 1 + 2 = 3 條 SQL，不是 1 + N。這是「我知道，但沒真的看過」的第一項。

第三件事跟上一個服務相反：這裡的 Delete 真的是 DELETE。上次那個服務因為 model 內嵌了 gorm.Model，db.Delete() 底下跑的其實是軟刪除的 UPDATE；這個 Product 沒有 DeletedAt 欄位，所以刪除就是刪除，查詢也不會被偷加 deleted_at IS NULL。同一個 ORM、同一行 API，形狀完全取決於你的 model 長什麼樣——而這件事只有把 SQL 攤開才看得到。

到這裡都還算「有趣但不驚訝」。真正讓我坐直的，是表格底下那一段——六條語句，次數整整齊齊都是 66。

六條一模一樣的 66

同一段四分鐘裡，面板上還有這幾條：

SQL次數
SELECT * FROM `products` WHERE `products`.`id` = ? ORDER BY `products`.`id` LIMIT ?67
SELECT * FROM `categories` WHERE `categories`.`id` = ?66
SELECT * FROM `suppliers` WHERE `suppliers`.`id` = ?66
INSERT INTO `categories` (`name`,`created_at`,`updated_at`,`id`) VALUES (?,?,?,?) ON DUPLICATE KEY UPDATE `id`=`id`66
INSERT INTO `suppliers` (`name`,`contact`,`created_at`,`updated_at`,`id`) VALUES (?,?,?,?,?) ON DUPLICATE KEY UPDATE `id`=`id`66
UPDATE `products` SET `name`=?,`description`=?,`price`=?,`quantity`=?,`category_id`=?,`supplier_id`=?,`created_at`=?,`updated_at`=? WHERE `id` = ?66

六條不同的語句，同一個次數。這種整齊不會是巧合——它們是同一條因果鏈上的六個節點。而且在面板的 Logs 分頁裡，它們就是連號的六列（#4293 到 #4298），照著順序排在一起。

那條鏈是這樣的，一次「使用者改了商品數量」的 PUT /api/v1/products/:id：

  1. controller 先用 id 把商品讀回來（FindByID，帶兩個 Preload）3 條 SELECT
  2. ShouldBindJSON 把請求的 JSON 蓋在這個「已經帶著 Category 和 Supplier 物件」的結構上—
  3. db.Save(product)：GORM 看到結構上掛著兩個關聯物件，先幫它們各做一次 upsert2 條 INSERT
  4. 最後才是真正的 UPDATE products1 條 UPDATE

而前端做的事，是最自然不過的：GET /products 拿到的 JSON 裡本來就帶著 category 和 supplier 兩個巢狀物件，改完數量原封不動 PUT 回去。你把讀到的東西原樣送回來，GORM 就認為你想連關聯一起存。

還有那條 UPDATE：它 SET 了每一個欄位，包括 created_at。Save 是全欄位寫回——不是「只更新你改的那兩欄」。

誠實一點：這件事有多嚴重

我不打算把它寫成災難，因為面板上的證據不支持：

  • 那兩條 INSERT … ON DUPLICATE KEY UPDATE `id`=`id` 是沒有副作用的。撞到既有主鍵時，它把 id 更新成 id——什麼都沒改。所以 categories 和 suppliers 的資料不會被這條路徑寫壞。
  • 但它仍然是一次寫入。 MySQL 這邊要走一次寫路徑、拿一次列鎖、進一次 binlog。四分鐘 132 次（66 + 66），只因為前端把讀到的物件原樣送回來。
  • 那條 SET 了 created_at 的全欄位 UPDATE 才是我比較在意的：它意味著任何沒被帶回來的欄位都會被寫成當初讀到的值。這一輪我沒有觀測到因此掉資料的證據——沒量到的我就不寫，只是把這條 SQL 的形狀擺在這裡。

觀測點本身也有盲區，一起說清楚：

  • 這一輪只掛了 Metric + Log，沒有量延遲，所以全篇不會出現任何毫秒數字。
  • 站在驅動門口看到的是帶 ? 佔位符的語句，參數是另外送的——所以面板上看得到「改了哪些欄位」，看不到改成什麼值。想看值就得再往下站一層，這一輪我沒有。
  • 掛在 GetStats 上那個計數點抓的是回傳值，而它在函式入口還是零值——所以面板上那條線是五條全零的序列，只能當「被呼叫過幾次」用，不能當統計值讀。這是我選點的代價，不是資料的意思。

看得到就是看得到，看不到就標明看不到。

然後我把那個頁面打開了

第二段四分鐘（16:23:31Z → 16:27:32Z），我什麼程式都沒改，只做了一件事：開一個瀏覽器分頁盯著那個庫存後台頁面——它的 refreshAll() 每秒跑一次，同時打 /categories、/suppliers、/products、/stats 四支 API。

同樣四分鐘，底下的 SQL 從 1,203 條變成 3,138 條。

多出來的 1,935 條是誰？把面板上的次數拆開來算就知道了：

那一秒的四支 API底下的 SQL條數
GET /categoriesSELECT * FROM `categories`1
GET /suppliersSELECT * FROM `suppliers`1
GET /products主查詢 + 兩條 IN 預載3
GET /statscount(*) × 3 + 一條 SUM(quantity), SUM(quantity*price)4

一次畫面刷新 = 9 條 SQL。 面板上 /stats 那四條語句這段窗口各出現 214 次，也就是頁面刷新了 214 次：9 × 214 = 1,926，跟實測多出來的 1,935 只差 9 條——剛好是一次刷新。數字自己兜起來了。

一個沒有人在操作、只是開著的頁面，每秒讓 MySQL 跑 8 條查詢。其中 SELECT * FROM `products` 是沒有 WHERE、沒有 LIMIT 的整表查詢，每秒一次。

這件事在 Metrics 分頁上更好看：FindAll 那條累積計數線，在 16:23:31 有一個明顯的斜率轉折——從每兩秒一次變成每秒一次多。而旁邊 Create 那條線是直的，斜率完全沒變。讀的行為被我打開的分頁改變了，寫的行為沒有，一眼就分得出來。

順帶對照一下服務自己的 log。Gin 的 access log 沒有瞎——這四分鐘它記了 1,698 行，每一行都是 200 / 201 / 204，該有的一行都沒漏：

GET /api/v1/products    335
GET /api/v1/categories  330
GET /api/v1/suppliers   330
GET /api/v1/stats       215

但 1,698 行 HTTP，底下是 3,138 條 SQL。access log 告訴你「請求成功了」，不會告訴你這些成功底下發了幾條查詢——HTTP 層的日誌天生就看不到扇出。那個把 1 變成 9 的倍率，只有站到驅動門口才數得出來。

（這份 access log 還幫我把更新鏈補完了：前四分鐘它記到 67 次 PUT，而面板上那條 FindByID 的 SELECT 剛好也是 67、後面五條卻是 66——那第 67 次的後半段跨過了窗口邊界。兩邊的數字連誤差都對得起來。）

收尾

我沒有改一行 code、沒有重啟服務、沒有先接一套 APM。就只是挑了驅動的兩個門口掛觀測點、在應用層放三個計數，然後認真看了八分鐘。

換來的是：我看到一次列表查詢是 3 條 SQL 而不是 N+1、看到這個服務的 Delete 是真刪不是軟刪、看到一次「改數量」在底下變成六條語句並且寫了三張表、看到 Save 會把 created_at 一起寫回去、最後看到一個沒人在操作的頁面每秒替我發 8 條查詢。

這些東西沒有一件是 bug 報告會告訴你的，也沒有一件需要重現步驟——它們一直都在跑，只是預設看不見。挑對位置站，它們自己就會現形。

  • 觀測點（共五個，全部動態掛載、不改原始碼）：
    • mysql.(*mysqlConn).QueryContext（go-sql-driver/mysql@v1.8.1/connection.go:510）—— log，模板 Q={query}，所有讀
    • mysql.(*mysqlConn).ExecContext（同檔 :529）—— log，模板 Q={query}，所有寫

    • repositories.(*ProductRepository).Create（product_repository.go:34）—— metric，純計數
    • repositories.(*StatRepository).GetStats（stat_repository.go:18）—— metric，抓回傳值（入口為零值，只能當計數用）

  • 觀測窗口：2026-07-25 16:19:33.700Z → 16:27:32.249Z（8 分鐘），16:23:31Z 分成兩段——前四分鐘沒開頁面 1,203 條（讀 800 / 寫 403），後四分鐘開一個每秒刷新的分頁 3,138 條（讀 2,724 / 寫 414）
  • 對帳：FindAll 計數 121 / 333 對上 SELECT * FROM `products` 的 121 / 333；Create 計數 114 / 115 對上 INSERT INTO products 的 114 / 115

  • 這一輪沒有掛 latency，所以全篇不出現任何毫秒數；驅動門口只看得到帶 ? 的語句，看不到參數值
