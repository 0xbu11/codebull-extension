前端改一次數量，資料庫收到三句寫入

2026-08-286 分 40 秒窗口 / 387 次改動 / 6 個觀測點Gin + GORM + MySQL 8.0

不改一行 code，對一個正在跑的 Gin + GORM + MySQL 服務，從 HTTP handler 一路掛到 driver 的門口，看六分四十秒。

為什麼掛在這裡

一個 PUT 進來，handler 讀出商品、改欄位、存回去——三行 Go。但這是三層框架疊起來的服務：Gin 的 handler、GORM 的 ORM、database/sql 的連線池、MySQL driver。每一層都可能自己多做一點事，而每一層都不會說。

所以掛法是「兩端夾」：上端是 handler 與 repository 的三個位置（改一個商品、先讀出商品、存回商品），下端直接掛在 driver 的門口——mysqlConn.QueryContext 與 ExecContext。那是語句離開行程的最後一道關卡，過了那裡就是網路。

事前可推：387 次 PUT、387 次 Save。不可推：driver 門口會收到幾句。

三種訊號各自在說什麼

metric（多常）——改一個商品 387、先讀出商品 774、存回商品 387。到了 driver 門口變成讀 2,322、寫 1,161。兩條 ×3 就是這樣量出來的。

latency（多久）——掛在 handler 那一段：p50 12ms、p95 13ms。分布很窄，代表這 387 次幾乎都走同一條路，沒有偶發的慢路徑。而這 12ms 裡面跑了六句 SQL。

log（什麼）——兩個 driver 節點各抓 query，這是整篇的關鍵證據。寫入那三句是：UPDATE products、INSERT INTO categories ... ON DUPLICATE KEY UPDATE、INSERT INTO suppliers ... ON DUPLICATE KEY UPDATE。我只改了數量，它連兩張關聯表都寫了一次。 讀的三句同理：products、categories、suppliers 各一句。

flamegraph（從哪來）——兩條框鏈，一條 31 格、一條 27 格，從 net/http 一路到 driver。這是全篇最長的堆疊，而它正好就是那句「三層框架疊起來」的實體證明：Gin 的中介層、GORM 的 callback、database/sql 的鎖與重試，全都在同一條鏈上。

結果

387 次 PUT，1,161 句寫入。 Save() 會把關聯一起存回去，那是 ORM 的預設行為——而預設行為只有數過才看得見。讀也是 ×3：兩個 Preload 各展開成一句 SELECT。

兩條虛線分別標著 11–16 層與 8–12 層未觀測，並把名字列出來：database/sql 的 QueryContext、retry、queryDC、withLock。那一段沒人掛點，圖就畫成一條有名字的虛線，而不是什麼都不畫。
