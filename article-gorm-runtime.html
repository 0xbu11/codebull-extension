I watched a running GORM for eight minutes, and saw it lose the primary key

2026-07-24 ~8 min window / 163 CRUD rounds gorm-demo + PostgreSQL 16

A few days ago I did something I don't usually do: without changing a single line of code, I attached two observation points inside GORM in a running Go service, then sat in front of the dashboard and watched.

Eight minutes in, I saw an UPDATE that should never have looked the way it did — it had lost its primary key and degenerated into the shape of a full-table update. This piece isn't really about a tool. It's about how much you can see simply by watching an ORM while it runs.

First decide where to stand

The annoying thing about an ORM is the layer it puts between "the line of Go you wrote" and "the SQL that actually reaches the database." You call db.Update(), and it builds the SQL, adds conditions, picks optimizations — none of which you can see in the source. You only find out once it runs.

So the first decision in observability is: which layer do you stand on. Too high (your business code) and you can't see the SQL. Too low (the database) and you can't trace it back to the code that sent it.

I picked GORM's internal convergence point — gorm.(*processor).Execute. Every Create / Preload / Update / Count / Delete in GORM eventually flows through this function. One entry, one exit, and you've cut the whole ORM in half. So I attached two points:

  • Entry (callbacks.go:82) — a pure counter, answering "how often does this convergence point get hit."
  • Exit (callbacks.go:140) — a point that pulls variables out, with the template SQL={string(stmt.SQL.buf)} | rows={db.RowsAffected} — rendering GORM's internal, not-yet-printed SQL buffer into a human-readable statement, and grabbing "how many rows were affected" along with it.

That rows field becomes the protagonist of this whole story. Points attached, the service kept running one CRUD round every three seconds, and I started watching.

What the first eight minutes showed: a CRUD round with no makeup on

The observation window was about eight minutes (starting 03:43:12Z, last entry 03:51:18Z, covering 163 rounds). The exit point recorded 1,045 SQL events, the entry point 2,090 hits, and after deduplication, 12 distinct statement shapes.

Start with the healthy half — in steady state, a full CRUD round with no makeup on (transcribed verbatim from the dashboard):

What I wroteThe SQL actually running, on the dashboardrowsCount
db.Create(&user)INSERT INTO "users" (...) VALUES ($1..$6) RETURNING "id"180
db.Create(&order)INSERT INTO "orders" (...) VALUES ($1..$6) RETURNING "id"180
db.Preload("User").First(...)SELECT * FROM "users" WHERE "users"."id" = $1 AND "users"."deleted_at" IS NULL180
(same line as above)SELECT * FROM "orders" WHERE "orders"."id" = $1 AND ... ORDER BY "orders"."id" LIMIT $2180
db.Model(&u).Update("Age", …)UPDATE "users" SET "age"=$1,"updated_at"=$2 WHERE "users"."deleted_at" IS NULL AND "id" = $3180
db.Count(&n)SELECT count(*) FROM "users" WHERE "users"."deleted_at" IS NULL1163
db.Delete(&oldest)UPDATE "users" SET "deleted_at"=$1 WHERE "users"."id" = $2 AND "users"."deleted_at" IS NULL175

This table alone contains two things I "knew about" but had never actually watched happen:

db.Delete() actually runs an UPDATE. Because the model embeds gorm.Model (which carries DeletedAt), the delete is quietly rewritten into a soft delete that stamps a timestamp. The data is still in the table — it's just marked.

Every read and write silently gets deleted_at IS NULL appended. That's the other half of soft deletes — every query automatically filters out deleted rows for you. You never wrote that condition, but it's on every single statement. And that db.Preload("User").First() line I assumed was one query? On the dashboard it's two SELECTs: one for orders, then another for users. A belongs-to preload is not a JOIN — it's a second trip. Scale that up to a list page and you have the beginning of N+1.

Up to here it's "interesting but not surprising." What made me sit up straight was the other half.

And then rows dropped to 0

The dashboard also carried another set of statements, nearly identical to the ones above with one difference — rows=0 — each appearing 83 times:

OperationSQLrowsCount
Create userINSERT INTO "users" (...) RETURNING "id"083
Create orderINSERT INTO "orders" (...) RETURNING "id"083
First(&order)SELECT * FROM "orders" WHERE "orders"."id" = $1 AND ...083
UpdateUPDATE "users" SET "age"=$1,"updated_at"=$2 WHERE "users"."deleted_at" IS NULL083

Four statements, the same rows=0, 83 times each, lined up neatly. But each of them hit zero for a different reason — and that's exactly the value of the rows column: one signal exposing four different failures at once.

  • Create user: the SQL did reach PostgreSQL and was rejected by a unique index (duplicate email, SQLSTATE 23505).
  • Create order: also reached the DB, blocked by a foreign key (fk_orders_user, SQLSTATE 23503) — because the user wasn't created in the previous step, user.ID was still 0, so the order carried user_id=0 and couldn't pass.
  • First(&order): this one genuinely ran; it just queried with id=0 and found nothing.
  • Update: this is the special one — it never reached the DB at all. More on that in a second.

rows=0 goes from a vague "it didn't work" to a set of clues you can trace one by one. The insidious thing about this class of failure is that nothing crashes — the program logs a line and keeps going. But on the dashboard, rows=0 is glaring, and with four of them side by side, the causality surfaces on its own.

What bothered me most: that UPDATE lost its primary key

Put the two versions of the UPDATE side by side, and you get the title of this piece:

-- healthy
UPDATE "users" SET "age"=$1,"updated_at"=$2 WHERE "users"."deleted_at" IS NULL AND "id" = $3
-- failing
UPDATE "users" SET "age"=$1,"updated_at"=$2 WHERE "users"."deleted_at" IS NULL

The same line of db.Model(&user).Update(...) produced two different SQL statements. The difference is that the latter lost AND "id" = $3 — it no longer updates "that one user," it updates "every user that hasn't been soft-deleted." This is the classic ORM footgun: the primary key isn't populated, and the update degenerates into the shape of a full-table update.

Why? Line up the counts of the four rows=0 statements on the dashboard — all 83 — and the causal chain surfaces by itself:

  1. Create user fails, user.ID is still 0rows=0 · 83×
  2. Create order carries user_id=0 and is rejected by the foreign keyrows=0 · 83×
  3. First queries with id=0 and finds nothingrows=0 · 83×
  4. Update, with user.ID at 0, can't have id = $3 built by GORM, so it degenerates into a WHERE carrying only the soft-delete scoperows=0 · 83×

But that degenerate UPDATE never actually hit the whole table. I cross-checked the service's own log: it returned rows=0 because GORM's built-in guard blocked it — WHERE conditions required (ErrMissingWhereClause) — taking 0.18 ms with zero DB round trips. In other words, the observation points let me see two things at once: GORM was building a full-table UPDATE that had lost its primary key, and GORM's own safety net caught it on the spot. The danger and the save, both laid out on the dashboard within one line.

That matters — because if someone ever disables that guard (db.Session(&gorm.Session{AllowGlobalUpdate: true})), this rows=0 becomes rows=thousands. And on the dashboard, you'd see that number jump immediately.

A comparison: why the built-in log still isn't enough

I also checked what the service's own GORM logger (default Warn level) printed. To be fair, it wasn't blind — during the failing phase it missed none of the four errors: duplicate key, foreign key, record not found, and that WHERE conditions required. It called them all out.

So what did the observation points add? Three things:

  1. It said nothing about the 600+ successful statements. The built-in logger is designed to be "quiet normally, loud on errors" — so you never get to see what healthy looks like, and you have no baseline to compare against.
  2. It only gives you error messages, not verbatim SQL. "WHERE conditions required" tells you something went wrong, but it doesn't show you what shape that degenerate UPDATE took. The dashboard does — every character of it.
  3. It doesn't reconcile. Entry 2,090 vs exit 1,045: that gap is itself information (the convergence point is entered roughly twice as often as SQL is actually emitted — GORM wraps single writes in an implicit transaction, and those transaction-control passes don't produce a recorded SQL statement at the exit). The day those two numbers diverge sharply is the day a batch of operations broke before SQL generation. The built-in logger can't give you that.

As for that entry counter — I didn't look at its "value," because it's a hit marker: every hit records a 1, so the value is always 1 and plots as a flat, information-free line. What's actually worth looking at is the cumulative view: a line climbing from 0 to 2,090, where the endpoint is the total hit count and the slope is the frequency. Interestingly, that line has an inflection point in the middle — going from 100 to 160 hits per 30 seconds — which is exactly the moment the service recovered from the failing phase and started doing more DB operations per round. A bare counter, viewed cumulatively, marks "when the service recovered" all by itself.

That's where the value of observability lies: it doesn't hand you "where the error is," it hands you a complete, symmetric, reconcilable record of the scene. Successes and failures treated alike. With that, a lot of bugs aren't "debugged" out of hiding by you — they surface on the dashboard by themselves.

Wrapping up: turning "invisible" into "visible"

I didn't change a line of code, didn't restart the service, didn't stand up a trace backend first. I just picked the right convergence point in a running process, attached two observation points, and paid attention for eight minutes.

What I got: I watched Delete actually run an UPDATE, watched every query silently carry deleted_at IS NULL, watched one Preload turn into two trips, watched four different reasons for rows dropping to 0, and finally watched an UPDATE lose its primary key in front of me — and get caught by GORM's guard on the spot.

An ORM is a black box, but a black box is only "invisible by default," not "impossible to see into." Stand in the right place, pull the variables out — what it ran should have been visible all along.
