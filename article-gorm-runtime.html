One Preload, one extra statement on the read path

2026-08-307m20s window / 143 rounds of CRUD / 7 probesGORM + PostgreSQL 16

📊 The numbers here come from this run’s remote dashboard: gorm-observing-runtime-20260830

Probes on a running GORM, from four API callers down to the line that emits the statement — no code change, seven minutes twenty.

Why these seven places

An ORM always has the same shape of problem: between the line of Go you wrote and the SQL that actually goes out sits a layer. Chained calls expand at run time, and how many statements they expand into is not something anybody tells you.

So the probes bracket it from both ends: four callers on top (Create, First, Update, Count), and at the bottom the convergence point every statement passes through, (*processor).Execute, plus the line that emits the statement. The top counts "how often I called"; the bottom counts "how often it actually ran". The difference between them is the answer.

Predictable up front: each caller's own count. Not predictable: whether they add up to the bottom.

What each signal says here

metric (how often) — Create 286, Find the first 286, Update 143, Count 143, convergence point 1,144. Every edge ratio is measured: three at ×1, one at ×1.5.

latency (how long) — on the convergence interval: p50 4.453ms, p95 64.295ms. A p95 fourteen times the p50 is what you get when INSERTs and SELECTs share one point — it measures "one ORM execution" without distinguishing the kind.

log (what) — the emit probe captures stmt.SQL.buf and lists the 8 distinct statements that left the process this round, 144 each. Among them is the SELECT * FROM "users" WHERE id = $1 that Preload expanded into, and the deleted_at IS NULL that soft-delete adds — neither of which I wrote.

flamegraph (from where) — the chains on the dashboard’s Call stack tab, the shortest only four frames (goexit · main · main · Create). The callers sit right under main; the deep part of the path is below the convergence point, and that stretch carries no probe, so the graph marks it with a dashed edge instead of leaving it blank.

What came out

Called 286 times, executed 429. The extra 143 come from Preload("User") — one chained call expanding into a second query at run time. That ratio is written in no line of code; you only get it by counting.

The edge is labelled 0–4 unobserved and names them: Find, preload, preloadEntryPoint, Preload — the extra query is emitted from inside those four frames.

One more gap is worth reading: 143 of the 1,144 executions have no upstream. That is Delete(), the one call this round with no probe on it. With the caller off the graph, its executions appear as a second starting point rather than being attached to somebody else.
