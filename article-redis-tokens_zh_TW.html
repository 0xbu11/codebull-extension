我盯著 Redis client 送上線的每一個 token，然後發現我存了一串不該存的東西

2026-07-24 觀測窗口約 5.5 分鐘 / 166 輪 redis-demo + Redis 7 + go-redis v9

前陣子我做了跟上次盯 GORM 一樣的事：不改一行 code，直接對一個正在跑的 Go 服務，在 Redis client 內部挑了兩個位置掛觀測點，然後坐下來看五分鐘。

你以為 rdb.HSet(ctx, "user:demo", "name", "CodeBull", "status", "active") 送出去的就是這一行。但真正爬上 TCP 連線的，是一串被拆開、依序寫出的 token。這篇想聊的還是同一件事——站對地方、把值抓出來，client 到底把什麼送上線，本來就該看得見。

先決定要站在哪一層看

Redis client 是一層 middleware：你呼叫 rdb.Incr()，它經過公開 API → hook 分派 → 重試迴圈 → 取連線 → 把命令編碼成 RESP → 寫進 socket。你的命令到底變成什麼、經過幾層，平常全看不到。

所以第一個決定一樣是：站在哪一層。我挑了兩個收斂點，一高一低：

  • 命令層（redis.(*Client).Process）——go-redis 所有單一命令（Incr、Set、HSet、SAdd、ZAdd…）最後都匯流到這裡。掛一個純計數，回答「總共送了幾個命令」。
  • 上線層（proto.(*Writer).string）——命令被寫進 socket 前，每一個字串參數（命令名、key、field、value）都會經過這個函式被寫出去。我在這裡把那個字串抓出來：token={s}。

第二個點的挑法有個講究。我一開始試過站更上面一點（收 interface{} 參數的那層），結果面板只看到 {type: 0x…, data: 0x…}——interface 的表頭、不是值。往下走，走到「每個字串被寫出去」的那個位置，抓到的就是乾淨的字串本身：incr、user:demo、CodeBull——一個一個、原樣、可讀。這個選擇等一下也會回頭補一句誠實話。

掛好，讓服務照常每兩秒跑一輪（INCR / SET / HSET / SADD / ZADD 五個命令），我開始看。

前五分鐘看到的：一行 Go = 一串依序上線的 token

觀測窗口大約五分半（09:49:58Z 起、166 輪），命令層記到 830 次命令，上線層記到 2822 個字串 token。攤開一輪，一行 rdb.HSet(...) 在線上其實是六個 token 依序寫出：

hset→ user:demo→ name→ CodeBull→ status→ active

你傳的每個 field / value，原封不動、照你給的順序上線。整輪五個命令的字串組成（逐字抄自面板）：

#我寫的 Go面板抓到的 token（逐字，依序）token
1rdb.Incr(ctx, "requests_total")incr · requests_total2
2rdb.Set(ctx, "last_run", t.String(), 0)set · last_run · <時間字串>3
3rdb.HSet(ctx, "user:demo", ...)hset · user:demo · name · CodeBull · status · active6
4rdb.SAdd(ctx, "active_users", "CodeBull")sadd · active_users · CodeBull3
5rdb.ZAdd(ctx, "leaderboard", ...)zadd · leaderboard · CodeBull3

每個穩定 token 都出現 166 次（跟輪數對得上），加起來 17 × 166 = 2822，跟面板總數一分不差。這種「數字自己兜得起來」的感覺，就是觀測值得信任的地方。到這裡都還算「有趣但不驚訝」。真正讓我坐直的是那個 <時間字串>。

然後我看到 SET 存進去的東西

demo 寫的是 rdb.Set(ctx, "last_run", t.String(), 0)。面板上，那個 value token 逐字是這樣：

2026-07-24 17:55:28.541657555 +0800 +08 m=+402.083349839

連 Go 執行期的單調時鐘 m=+402.08… 都一起被塞進 Redis 了。

t.String() 到底序列化成什麼，我平常從來不會去想——反正「存個時間」嘛。但面板逐字攤開來，我才看到我存的不是一個乾淨的時間戳，而是一整串 Go 內部表示法：牆上時鐘 + 時區 + 單調時鐘讀數。這東西你之後要拿來比較、排序、或跨機器解析，全都會出問題（單調時鐘只在這個 process 裡有意義）。

這不是 bug、程式也沒報錯——它就只是一個你以為你知道、其實沒真的看過的東西。觀測的價值就在這：它不等你出事，它讓你在存進去的那一刻就看見。

一個誠實話：面板對「型別邊界」不裝

看 ZADD 那條，面板抓到的是：

zadd · leaderboard · CodeBull

少了一個東西——分數。redis.Z{Score: float64(val), ...} 的 score 是個 float64，而數字在 client 內部走的是另一個編碼器（轉成 ASCII bytes 的那條路），不經過我這個「字串」觀測點。所以這一輪，我看得到 zadd、leaderboard、CodeBull，就是看不到那個分數值。

我大可以把觀測點換到更底層、把數字也一起撈進來——但那樣面板每一行會拖著一長串 byte 陣列，變得很難讀。我選擇了乾淨、可讀、只看字串，然後老實告訴你：這裡有個型別邊界，字串看得到、數字在別的門。看得到就是看得到，看不到就標明看不到，不給你一個假裝完整的東西——這對觀測來說反而是最重要的品質。

順帶一個對得上的小數字：字串 CodeBull 一輪出現三次（HSET value + SADD member + ZADD member），面板實測 498 次 = 3 × 166。同一個字串在三個資料結構裡被重複送上線——這種「其實你送了三遍」的事，平常不攤開也不會注意到。

順便對個帳

命令層 830、上線層 2822 個字串 token。這兩個數字擺在一起就是一種健康檢查：830 個邏輯命令，展開成 2822 個字串 token，平均一個命令 3.4 個字串——跟「五個命令、17 個字串 token 一輪」完全吻合。

哪天這個比例歪掉（命令數沒動、token 數暴增），那就是有人在某條命令裡塞了異常多的參數（大 batch、爆量的 HSET field）。有這兩個點同時看，你不用猜，面板先幫你把「命令」和「它在線上的重量」分開量好。

收尾

我沒有改一行 code、沒有開 client 的 debug log、沒有抓 tcpdump 去解 RESP。就只是在一個跑著的 process 上，挑了「命令收斂點」和「寫 socket 的字串出口」兩個位置，把值抓出來，看了五分半。

換來的是：我看到一行 HSet 其實是六個依序上線的 token、看到我把一整串帶單調時鐘的 time.Time 存進了 Redis、看到同一個字串一輪被送了三遍、也清楚知道哪一個型別是我這個觀測點看不到的。

client 是個黑盒子，但黑盒子只是「預設看不見」，不是「不能看」。它把什麼送上線，本來就該看得見。

附：這次的觀測設定（可重現）

  • 收斂點：
    • redis.(*Client).Process:706（metric，命令計數，變數過濾只留 trace_hits，面板才乾淨）
    • proto.(*Writer).string:166（log，抓 token={s}——每個字串參數寫進 socket 的必經之地，面板顯示乾淨可讀的字串）
  • 被觀測的服務：每 2 秒一輪 5 命令（INCR/SET/HSET/SADD/ZADD）的 redis-demo + Redis 7（docker，port 6380）+ vendored go-redis v9（redis_pkg/）
  • 觀測窗口：2026-07-24 09:49:58Z → 09:55:28Z（約 5.5 分鐘 / 166 輪），命令 830、字串 token 2822，穩定 token 各 166、CodeBull 498（3×/輪）、SET 時間字串 166（每輪唯一）
  • 型別邊界：ZADD 的 float 分數走數字編碼器（w.int/w.float），不經過字串出口，所以本輪不在字串觀測點的視野內——誠實揭露，不杜撰
  • 這一輪只掛 Metric + Log、沒有量延遲（latency 掛在 client 的 per-call 熱路徑會弄掛觀測橋接），所以全篇不寫任何毫秒數

這篇裡「不改 code、對執行中的 process 掛觀測點、然後盯著看」用的是 CodeBull —— 一個 VS Code extension，能對正在跑的 Go 服務動態插入 Metric / Log / Latency 觀測點，不改原始碼、不重編譯、不重啟。上面那串把單調時鐘一起存進 Redis 的 SET，就是這樣被我當場看到的。
