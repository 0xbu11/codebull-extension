One convergence point, three truths: measuring how often, what, and how long on a running GORM

2026-07-23 5.0 min observation window gorm-demo + PostgreSQL 16 (fresh volume)

Driven end to end by an AI agent through the CodeBull MCP server: attach observation points → collect evidence → write from the evidence → upload the remote dashboard. Every SQL statement and every number below comes from this round's evidence.json, none of it invented.

"What is my ORM actually doing?" is really three questions:

  • How often does it happen? (which operation is hottest)
  • What happened? (what the SQL actually sent looks like)
  • How long did it take? (where the p95 tail hides)

Normally, answering all three at once means three tools and three rounds of code changes. This time I attached three observation points to one convergence point inside GORM, and measured all three truths in five minutes — with zero source changes, and even the dashboard built by the agent.

Why "all at once" is hard

An ORM is a black box. To look inside it:

  • ❌ Turn on Debug() for the SQL — but you get no latency distribution, and the default logger only speaks up on errors
  • ❌ Bring in an APM for p95 — but first you have to embed an SDK and stand up a backend
  • ❌ Count the calls yourself — another round of editing, rebuilding, redeploying

Three questions, three toolchains, three trips into the source. And all three happen inside the same function.

How the setup works: one convergence point, three observation points

Every CRUD operation in GORM passes through gorm.(*processor).Execute. I attached three dimensions to it (all driven by the agent over MCP):

① Metric (how often) — hit counter at the Execute entry

codebull_register_tracepoint  path: gorm_pkg/callbacks.go  line: 82   kind: metric

② Log (what happened) — Execute exit, where the SQL has been generated

codebull_register_tracepoint  path: gorm_pkg/callbacks.go  line: 140  kind: log
  template: "SQL={string(stmt.SQL.buf)} | rows={db.RowsAffected}"

③ Latency (how long) — wall-clock for Execute's DB segment (callback chain + logging)

codebull_register_tracepoint  path: gorm_pkg/callbacks.go  line: 83 → endLine: 150  kind: latency
  template: "p50(latency), p95(latency), p99(latency), avg(latency)"

Three points, and the dashboard starts emitting "counts / verbatim SQL / millisecond distribution" simultaneously. No code changes, no restart.

Four things the dashboard showed me

1. The tail is 10× the median (p50 5.7 ms → p95 60 ms)

Half of all Execute calls finish within 5.7 ms, which sounds fast. But p95 shoots to 60 ms, p99 to 64 ms, and the slowest to 99 ms — the tail is more than ten times the median. This is exactly where looking only at "avg 11 ms" fools you: the average dilutes the tail, and what actually bites your SLA is that 5%. Without a latency observation point you'd only see "the average is fast," then get ambushed by p99 in production.

2. db.Delete() actually runs an UPDATE (statement #8)

The demo calls db.Delete(&oldest), but the dashboard shows what went out was UPDATE "users" SET "deleted_at"=$1 .... That's GORM's soft delete: because the model embeds gorm.Model (carrying DeletedAt), Delete is quietly rewritten into an UPDATE that stamps a deletion timestamp. The data is still in the table.

3. Invisible conditions you never wrote + one Preload = two SELECTs

Across all eight statements, every read and write automatically gets "deleted_at" IS NULL appended — the other half of soft deletes, keeping deleted rows out. And the single line db.Preload("User").First(...) shows up on the dashboard as two SELECTs: one against orders, and a separate one against users (112 each). A belongs-to association isn't a JOIN — it's an extra trip, which on a list page becomes a breeding ground for N+1.

4. Entry 947 ≈ exit 917: the power of reconciliation

Metric entry 947, log exit 917, a gap of ~30. That gap is itself information: roughly 30 Execute calls entered the convergence point without producing a recorded SQL statement at the exit (DryRun / empty-SQL transaction-control paths). The day those two numbers diverge sharply is the day a batch of operations broke before SQL generation — with both points running, you don't have to guess; the dashboard reconciles for you.

Honest disclosure: what was actually measured

All three dimensions here — Metric / Log / Latency — are real data measured in this round, latency in particular: it's the latency_ms distribution genuinely captured with kind:latency (entry Execute:83 → exit line 150), not an estimate. The raw variables on Execute:82 (curTime / err / optimizer internals) are not cited, because they're raw instrument values, not trustworthy statistics. Every number on the dashboard has to be traceable — that's the floor.

How to reproduce this (3 steps)

  1. Search for CodeBull in VS Code and install it, then start your Go project (remember to compile with debug flags: -gcflags="all=-dwarflocationlists=true -N -l", so CodeBull can resolve variable locations and line numbers).
  2. Attach three observation points at the ORM's convergence point: Metric at the entry, Log at the exit (template SQL={string(stmt.SQL.buf)} | rows={db.RowsAffected}), and a Latency span (entry→exit). Or just let an AI agent call codebull_register_tracepoint over the CodeBull MCP server.
  3. Let real traffic run for 5 minutes, then open the dashboard: Metric for frequency, Log for verbatim SQL, Latency for the p95/p99 tail.

No code changes, no restart, no redeploy. What your ORM ran, and how long it took, should be visible.
