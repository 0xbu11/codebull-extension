When Set() returns true, nothing has been decided yet

2026-08-286.5-minute window / 103,432 misses / 4 probesristretto v2

Probes on a running ristretto, from the caller down to the line that runs the admission policy — no code change, six and a half minutes.

Why both sides at once

cache.Set(key, value, 1) returns a bool. The intuitive reading is "did it store". But ristretto is a cache with an admission policy: it weighs a new key against what it already holds and decides whether to keep or drop it. So which of those does that true mean?

Answering requires standing on both sides at the same time: the caller (miss, issue the Set) and the line inside the library that actually decides, defaultPolicy.Add. Either alone fails — from the caller you only ever see true; from inside you cannot tell whose request it belongs to.

The load is designed too: first a keyspace of 2,000 (twice the capacity), then 50,000 (fifty times). Same code, two pressures.

What each signal says here

metric (how often) — 103,432 misses, 102,314 reaching the Set, ×0.99. The caller's line is about as clean as it gets. But those 101,918 admission decisions do not hang off that line — they are their own starting point.

latency (how long) — p50 0.17ms, p95 0.27ms. A cache write is a sub-millisecond operation, and the point here is *how fast*: the caller barely waits, because the real trade-off is not on this path at all.

log (what) — the most important column here, because the two nodes captured different kinds of thing entirely. The caller captured strings like key-000008, key-000029. The policy captured key=5730345252726497000 cost=57 — a 64-bit hash and a cost. It is not comparing the string you are holding.

In the first stretch each key is written a dozen-odd times per ten seconds; past the middle the same keys drop to single digits. Drag the timeline there and those rows change on their own — that is the moment the keyspace went from 2,000 to 50,000.

flamegraph (from where) — three frame chains, and the contrast reads in one glance:

Cache miss        goexit · main · main · workload
Admit or reject   goexit · NewCache · processItems · Add

That goroutine was started by NewCache when the cache was built.

What came out

Set() returning true means "this request was accepted", not "this key was kept". The real trade-off happens later on another goroutine, comparing hash and cost.

The two counts differ by 396 — the part not yet processed when the window closed. That difference is itself the evidence: if the decision were synchronous, the two sides would always be equal.
