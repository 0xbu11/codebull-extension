我盯著一個跑著的 GORM 看了八分鐘，然後看到它把主鍵弄丟了

2026-07-24 觀測窗口約 8 分鐘 / 163 輪 CRUD gorm-demo + PostgreSQL 16

前幾天我做了一件平常不太會做的事：不改任何一行 code，直接對一個正在跑的 Go 服務，在 GORM 內部掛了兩個觀測點，然後就坐在面板前面看。

八分鐘，我看到一條本來不該長成那樣的 UPDATE——它把主鍵弄丟了，退化成一條「更新全表」的形狀。這篇想聊的不是什麼工具，而是「盯著執行中的 ORM 看」這件事本身，能讓你看到多少平常看不到的東西。

先決定要站在哪裡看

ORM 最麻煩的地方，是它把「你寫的一行 Go」和「真正送到資料庫的 SQL」之間隔了一層。你呼叫 db.Update()，它幫你拼 SQL、加條件、選最佳化——這些你在原始碼裡是看不到的，得等它跑起來才知道。

所以觀測的第一個決定是：站在哪一層看。站太上層（你的業務程式）看不到 SQL；站太下層（資料庫）又跟不回是哪段程式送的。

我挑了 GORM 內部的收斂點——gorm.(*processor).Execute。GORM 所有的 Create / Preload / Update / Count / Delete，最後都會匯流到這個函式。一進一出，剛好把整個 ORM 攔腰看穿。於是我掛了兩個點：

  • 入口（callbacks.go:82） 放一個純計數，回答「這個收斂點多常被打到」。
  • 出口（callbacks.go:140） 放一個把變數抓出來的點，模板是 SQL={string(stmt.SQL.buf)} | rows={db.RowsAffected}——把 GORM 內部那串還沒印出來的 SQL buffer 直接渲染成人看得懂的語句，順手把「影響了幾列」一起帶出來。

rows 這個欄位，等一下會變成整篇的主角。掛好，讓服務照常每三秒跑一輪 CRUD，我就開始看。

前八分鐘看到的：一輪 CRUD 的素顏

觀測窗口大約八分鐘（03:43:12Z 起、最後一筆 03:51:18Z，涵蓋 163 輪），出口那個點記到 1045 筆 SQL，入口 2090 次命中，去重之後是 12 種不同的語句形狀。

先看健康的那半邊——穩態下，一輪 CRUD 的完整素顏（逐字抄自面板）：

我寫的面板上真正跑的 SQLrows次數

db.Create(&order)INSERT INTO "orders" (...) VALUES ($1..$6) RETURNING "id"180

光是這張表，就有兩件我平常「知道，但沒真的看過」的事：

db.Delete() 底下跑的其實是 UPDATE。 因為 model 內嵌了 gorm.Model（帶 DeletedAt），刪除被默默改寫成蓋一個時間戳的軟刪除。資料還在表裡，只是被標記了。

每一條讀寫都被偷偷加上 deleted_at IS NULL。 這是軟刪除的另一半——所有查詢都自動幫你把已刪的列擋掉。你沒寫這個條件，但它每一條都在。還有那句 db.Preload("User").First()，我以為是一次查詢，面板上卻是兩條 SELECT：一條查 orders、一條再補查 users。belongs-to 的 preload 不是 JOIN，是再跑一趟。放大到列表頁，這就是 N+1 的起點。

到這裡都還算「有趣但不驚訝」。真正讓我坐直的是另外半邊。

然後 rows 掉到 0

面板上同時還有另一組語句，長得跟上面幾乎一樣，只有一個差別——rows=0，而且各出現了 83 次：

操作SQLrows次數
Create userINSERT INTO "users" (...) RETURNING "id"083
Create orderINSERT INTO "orders" (...) RETURNING "id"083
First(&order)SELECT * FROM "orders" WHERE "orders"."id" = $1 AND ...083
UpdateUPDATE "users" SET "age"=$1,"updated_at"=$2 WHERE "users"."deleted_at" IS NULL083

四條語句，同一個 rows=0，各 83 次，整整齊齊。但它們掉到 0 的原因其實各不相同——而這正是 rows 這一欄的價值：它用同一個訊號，把四種不同的失敗一次照出來。

  • Create user：SQL 有送到 PostgreSQL，被 unique index 打回（email 撞號，SQLSTATE 23505）。
  • Create order：也送到 DB，被外鍵擋下（fk_orders_user，SQLSTATE 23503）——因為上一步 user 沒建成，user.ID 還是 0，order 帶著 user_id=0 自然過不了。
  • First(&order)：這條真的跑了，只是拿 id=0 去查、什麼都沒找到。
  • Update：這條最特別——它根本沒送到 DB。等一下講。

rows=0 從一個含糊的「沒成功」，在面板上變成一組可以逐條追因的線索。這種失敗最陰險的地方在於——程式沒有 crash，它記一行 log、然後繼續往下跑。但在面板上，rows=0 是刺眼的，而且四條並排，因果自己就浮出來。

最讓我在意的：那條 UPDATE 把主鍵弄丟了

把兩組的 UPDATE 並排看，就是這篇標題的來源：

-- 健康時
UPDATE "users" SET "age"=$1,"updated_at"=$2 WHERE "users"."deleted_at" IS NULL AND "id" = $3
-- 失敗時
UPDATE "users" SET "age"=$1,"updated_at"=$2 WHERE "users"."deleted_at" IS NULL

同一行 db.Model(&user).Update(...)，生出了兩種 SQL。 差別是後者的 AND "id" = $3 不見了——它不再是更新「那一個 user」，而是「所有還沒被軟刪除的 user」。這就是 ORM 最經典的 footgun：主鍵沒填好，更新退化成全表更新的形狀。

為什麼會這樣？把面板上四條 rows=0 的次數排在一起看——全是 83——因果鏈自己就浮出來了：

  1. Create user 失敗，user.ID 還是 0rows=0 · 83 次
  2. Create order 帶著 user_id=0，被外鍵擋下rows=0 · 83 次
  3. First 拿 id=0 去查，什麼都沒找到rows=0 · 83 次
  4. Update 因為 user.ID 是 0、GORM 拼不出 id = $3，退化成只剩軟刪除範圍的 WHERErows=0 · 83 次

但這條退化的 UPDATE，最後並沒有真的跑到全表。 我去對了一下服務自己的 log：它 rows=0，是因為 GORM 內建的防護把它攔下了——WHERE conditions required（ErrMissingWhereClause），耗時 0.18 毫秒、沒有任何一次 DB round trip。也就是說，觀測點讓我同時看到了兩件事：GORM 正在拼一條把主鍵弄丟的全表 UPDATE，以及 GORM 自己的安全網當場接住了它。 危險和保命，一行之內都攤在面板上。

這很重要——如果哪天有人關掉了這層防護（db.Session(&gorm.Session{AllowGlobalUpdate: true})），這條 rows=0 就會變成 rows=幾千。而你在面板上，會立刻看到那個數字跳起來。

一個對照：內建的 log 為什麼還不夠

我順手比對了服務自己的 GORM logger（預設 Warn level）印了什麼。公平講，它其實沒有瞎——失敗那段，四種錯誤它一種都沒漏：duplicate key、foreign key、record not found、還有那條 WHERE conditions required，全喊了。

那觀測點多給了什麼？三件事：

  1. 成功的那 600 多筆，它一句都沒說。 內建 logger 的設計就是「平常安靜，出事才叫」——所以你永遠看不到「健康長什麼樣」，也就沒有基準去比對。
  2. 它只給你錯誤訊息，不給你逐字 SQL。「WHERE conditions required」告訴你出事了，但沒把那條退化成什麼形狀的 UPDATE 攤給你看。面板有——一個字都不少。
  3. 它不對帳。 入口 2090、出口 1045，這個差距本身就是資訊（收斂點被進入的次數，約是真正吐出 SQL 的兩倍——GORM 把單筆寫入包了一層隱式交易，那些交易控制的進出不會在出口生出一條被記錄的 SQL）。哪天這兩個數字大幅背離，就是一批操作在生成 SQL 前就出事了。內建 logger 給不了你這個。

那個入口計數，我沒有看它的「值」——因為它是個命中標記，每打到一次就記一個 1，值永遠是 1、畫出來是條沒資訊的平線。真正好看的是把它累加起來：一條從 0 爬到 2090 的線，終點就是總命中數，而斜率就是頻率。有意思的是這條線在中途有個轉折——每 30 秒從 100 次變成 160 次——那正是服務從失敗相位恢復、每輪 DB 操作變多的那一刻。一個裸計數，只要換成累積來看，連「服務什麼時候恢復的」都自己標出來了。

觀測的價值就在這裡：它給你的不是「哪裡報錯了」，而是一份完整、對稱、可對帳的現場記錄。成功和失敗一視同仁。有了這個，很多 bug 不是被你「除錯」除出來的，是它自己在面板上現形的。

收尾：把「看不見」變成「看得見」

我沒有改一行 code、沒有重啟服務、沒有先埋一套 trace backend。就只是在一個跑著的 process 上，挑對收斂點掛了兩個觀測點，然後認真看了八分鐘。

換來的是：我親眼看到 Delete 其實在 UPDATE、看到每條查詢都偷帶 deleted_at IS NULL、看到一次 Preload 是兩趟查詢、看到 rows 掉到 0 的四種不同原因、最後看到一條 UPDATE 在我眼前把主鍵弄丟、又被 GORM 的防護當場接住。

ORM 是黑盒子，但黑盒子只是「預設看不見」，不是「不能看」。挑對地方站、把變數抓出來——它跑了什麼，本來就該看得見。
