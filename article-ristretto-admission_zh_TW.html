Set() 回你 true 的時候，收不收還沒決定

2026-08-286.5 分鐘窗口 / 103,432 次沒中 / 4 個觀測點ristretto v2

不改一行 code，對一個正在跑的 ristretto 從呼叫端一路掛到入場政策那一行，看六分半。

為什麼掛在這裡

cache.Set(key, value, 1) 回傳 bool。直覺會讀成「有沒有存進去」——但 ristretto 是有入場政策的快取：它會拿新 key 的價值跟現有的比，決定收留還是拒收。那麼那個 true 到底代表哪一件事？

要回答就得同時站在兩邊：呼叫端（沒中、送出寫入）和函式庫內部真正做決定的那一行（defaultPolicy.Add）。只掛一邊都答不了——只有呼叫端，你看到的就是 true；只有內部，你不知道它對應到誰的請求。

負載也是設計過的：前半 keyspace 2,000（容量的兩倍），中途換成 50,000（五十倍）。同一份程式碼，兩種壓力。

三種訊號各自在說什麼

metric（多常）——沒中 103,432、送出寫入 102,314，×0.99。呼叫端這條線乾淨得毫無懸念。但入場決定那 101,918 次不掛在這條線上——它自己是一個起點。

latency（多久）——p50 0.17ms、p95 0.27ms。快取寫入是次微秒級的操作，這裡的意義在於它有多快：呼叫端幾乎沒等，因為真正的取捨根本不在這條路徑上。

log（什麼）——這是全篇最關鍵的一欄，而且兩個節點抓到的東西根本不是同一種。呼叫端抓的是 key-000008、key-000029 這種字串；入場政策抓的是 key=5730345252726497000 cost=57——一個 64 位元的 hash 和一個成本值。它比的不是你手上的字串。

前半每個 key 每十秒被寫十幾次，中段之後掉到個位數——把時間軸拉過去，那幾行的次數會自己變。那就是 keyspace 從 2,000 換成 50,000 的那一刻。

flamegraph（從哪來）——三條框鏈，對比一眼就看完：

快取沒中        goexit · main · main · workload
決定收留或拒收   goexit · NewCache · processItems · Add

那條 goroutine 是 NewCache 建快取的時候自己開的。

結果

Set() 回 true 只代表「這個請求被收下了」，不代表「這個 key 被留下來了」。真正的取捨稍後在另一條 goroutine 上發生，比較的是 hash 與 cost。

兩個數字差 396——那是窗口結束時還沒被處理完的部分。這個差額本身就是證據：如果決定是同步的，兩邊應該永遠相等。
