我盯著一個跑著的 etcd 看了九分鐘，然後看到它的 fsync 在忙的時候比閒的時候快十四倍

2026-07-28 9 分鐘窗口 / 8,390 次寫入 / 20 個觀測點 etcd v3.7 單節點

前幾天我做了一件平常不太會做的事：不改任何一行 code，直接對一個正在跑的 etcd，把它從 gRPC 收下一個 put、到磁碟上那一次 fdatasync 為止的整條路掛滿觀測點，然後坐著看九分鐘。

不是挑幾個「最關鍵的層」看看而已——是那條路上每一個我叫得出名字的關卡，二十個位置，同時看。不重編譯、不重啟。

我原本想看的是「一次寫入在裡面被拆成幾件事」。結果最後讓我坐直的，是一件跟次數完全無關的事：同一行 fdatasync，在每秒只寫一筆的時候要花 5.9 毫秒，在全速灌的時候只要 0.4 毫秒。越閒越慢。這篇聊的不是工具，是「盯著執行中的東西看」這件事本身。

先決定要站在哪裡看

etcd 的黑盒性質很特別：它不像 ORM 那樣「你寫的一行變成什麼 SQL」，而是「你送的一個 key，要被幾層各自有節奏的機制輪流處理過，才算真的寫進去」。gRPC 收下、包成 raft 提案、寫進 WAL、fsync、等提交、套用到狀態機、寫進 MVCC、更新記憶體索引、丟進 bbolt 的交易緩衝、最後某個時刻整批落盤。

從外面，你只看得到 OK。

通常掛觀測點的做法是挑幾個代表性的關卡，中間用推測接起來。這次我想試試看不推測——把每一層的入口都放一個點，讓比例自己說話。二十個位置是這樣分配的：

有三個點我要先講清楚，因為它們是這篇的骨架。

落盤那個點，我沒有只放一個計數器。 「這段時間落盤幾次」這個數字本身其實不太說明問題——真正想問的是每一次落盤到底攤了多少工作。commit() 裡剛好有一個決定要不要落盤的計數器 t.pending，所以我把它直接抓出來當 log 模板。每一次落盤攤了幾筆，逐次寫在面板上。

兩條 latency 線，一開始一個樣本都收不到。 註冊回報成功、狀態顯示已插樁，hitCount 也在跳，但延遲那張表整個是空的。後來我試著在註冊時多給一個 template 別名（wal_fsync_latency），同一行、同一個 process，樣本就出來了——最後收到 8,380 個。同一件事、換個掛法，從「量不到」變成「量得到」，這種踩坑我覺得比結論本身還值得寫。

還有一個點，我掛上去了，但它從頭到尾一次都沒響。 就是那個 100ms 的 backend 批次計時器。留到誠實段講。

負載我刻意讓九分鐘長得不一樣，五個相位：兩分鐘完全不碰它 → 兩分鐘每秒寫一筆 → 兩分鐘一個 client 全速灌 → 兩分鐘四個 client 一起灌 → 一分鐘只讀不寫。

前兩分鐘：一個沒人使用的 etcd

觀測窗口是 2026-07-27 16:15:08.635Z 到 16:24:11.029Z，九分零二秒。第一段兩分鐘，我一個字都沒送給它。

二十個點裡面，只有一個動了：raftNode.tick，1,200 次。120.03 秒，正好每秒 10 下，對得上 etcd 預設的 100ms tick。

其他十九個全是 0。gRPC 是 0、提案是 0、WAL 是 0、fsync 是 0、MVCC 是 0、落盤是 0。我去對了 etcd 自己的 /metrics，同期 etcd_disk_wal_fsync_duration_seconds_count 和 etcd_disk_backend_commit_duration_seconds_count 的差值也都是 0。

一個閒置的 etcd 不是在空轉磁碟，它只是在數拍子。 這件事我「知道」，但沒真的看過整條路同時安靜下來長什麼樣——十九個點一起壓在 0 上，只有心跳在走。

一次 etcdctl put，在我掛的十六個位置上總共留下二十三個腳印。

有三個「2」和一個「3」是我以為我知道、其實沒真的看過的：

  • WAL.Save 是兩次，saveEntry 只有一次。 一次寫入在 WAL 上是兩輪：一輪把 entry 附加進去，另一輪只更新 hard state（提交索引往前）。第二輪沒有 entry，所以 MustSync 判定不必 fsync——WAL.Save 228 次，但 WAL.sync 只有 114 次。寫入輪數跟落磁碟次數不是同一件事。
  • applyAll 也是兩次。 raft 的 Ready 迴圈為同一筆寫入轉了兩圈（一圈附加、一圈提交後套用），但真正被套用的 entry 只有一個。
  • unsafePut 是三次。 一次寫入在 bbolt 這一層是三筆 key/value：使用者那筆進 key bucket，另外兩筆是 etcd 自己的 meta（consistent index 之類）。

MVCC 那個點抓到的逐字內容長這樣：

k=steady/key-0 rev=2
k=steady/key-113 rev=115

修訂號一筆一號往上跑。那個 rev，最後會變成我驗算整篇文章的尺。

順手做的對照：只讀不寫的時候，這二十個點動了幾個

最後一分鐘我只發 etcdctl get，61.9 秒送了 5,276 次。二十個點裡面動的有幾個？

三個。 Range 5,276 次，applyAll 和 applyEntries 各 5,380 次。

其餘全部是 0——沒有提案、沒有 WAL entry、沒有 fsync、沒有 MVCC 寫入、沒有 bbolt 落盤。（面板上這個相位還掛著 116 筆 conc/ 開頭的紀錄，逐字看 key 就知道那是上一個相位的尾巴溢出來的，不是這裡產生的。）

有意思的是那個 5,380：一次線性化讀取，還是要讓 raft 的 Ready 迴圈轉一圈。它不寫任何東西，但它不是免費的。

然後我把負載推上去，看哪幾欄開始脫隊

第三段一個 client 全速灌，兩分鐘 4,038 筆（約 33.8/s）。第四段換成四個 client 一起灌，兩分鐘 4,238 筆。

WAL 幾乎完全不批次。 整個九分鐘 8,390 筆寫入，8,379 次 fsync——只省下 11 次，佔 0.13%。而且那 11 次全部發生在四 client 那一段。

這裡我要老實說一句：第四相位是我特地設計來抓 WAL 批次化的，然後它幾乎沒發生。 我的想法是「多個 client 同時送，raft 就會把好幾個 entry 塞進同一輪 Ready，於是好幾筆寫入共用一次 fsync」。機制是對的，而且面板上找得到它的殘影：WAL.saveEntry 全程 8,390 次，跟客戶端寫入一比一；但 WAL.Save 是 16,739 次，比「每筆寫入兩輪」的 16,780 少了 41 輪。有幾輪 Save 確實塞進了不只一個 entry。它真的發生了，只是幾乎沒發生。（少掉的 41 輪 Save 和省下的 11 次 fsync 兜不成一個乾淨的比例，這中間還有我沒看清楚的東西。）我的四個 client 加起來也只推到每秒 35 筆，隊列根本沒排起來。預測方向對、量級完全落空——這比預測成功值得寫。

那每一次落盤，到底攤了幾筆？

「9.72 比 1」是個平均值，而平均值最會騙人的地方就在這裡：它可能是每次都攤 9 到 10 筆，也可能是有的攤兩筆、有的攤三十筆。這兩種情況對儲存層的意義完全不一樣，但算出來的平均值一模一樣。

所以我在落盤那個點抓的不是次數，是 pending 本身。全窗口 1,331 次落盤，逐次攤開來是這樣：

每秒一筆的時候，114 次落盤，每一次都剛好是 3，沒有任何一次例外。 一筆寫入、三筆 bbolt 操作、一次落盤，一比一比一，乾淨到有點無聊。

而且這兩組數字都不是雜訊堆出來的平均：每秒一筆那 114 個樣本，p50 到 p99 從 5.901 到 6.292——整組緊緊貼在 6 毫秒上；全速那 3,930 個樣本，p50 到 p95 從 0.405 到 0.506——整組緊緊貼在 0.4 毫秒上。兩個都是很窄的分佈，只是落在完全不同的地方。

為什麼？我不知道。 我能講的只有我量到的東西：這是同一個 process、同一個 WAL 檔案、同一行 fdatasync，唯一改變的是它被呼叫的頻率。至於那 5.5 毫秒的差額是花在裝置的寫入快取上、還是檔案系統上、還是 CPU 從閒置狀態爬回來的時間——在 process 裡面看不出來，我不打算掰一個機制給讀者。

但這件事對「怎麼讀 p99」是有意義的：如果你在低流量時段量 etcd 的 fsync 延遲，然後拿那個數字當 SLO 基準，你會嚴重高估你系統忙起來的時候的成本。

誠實話：這一輪我搞砸的、看不到的、和說不準的

我第一次跑出來的數字全部是錯的，而且錯得很好看。 正式窗口之前我先跑了一次排練，那一輪送出 2,721 筆寫入之後，面板上 gRPC 入口的累計命中數才 1,685 次、server API 1,332 次、raft 提案 1,131 次——連那一輪自己送出的筆數都不到，而且每個點少的幅度還不一樣。沒有任何警告。查下去才發現 SDK 預設帶一個每秒 1,000 事件的 token bucket，超過就靜靜丟掉——我二十個點掛在寫入路徑上，大概每秒 44 筆客戶端寫入就撞頂了。把上限調高之後重跑一次控制實驗（480 筆、八路併發），每一個點都跟 etcd 自己的計數器一分不差，正式窗口的 8,390 筆也是七組交叉核對全部吻合。這一段本來可以不寫，但「看起來合理的錯數字」正是觀測工具最危險的失敗模式，我寧可把它攤開。

有一個點我掛上去了，它從頭到尾一次都沒響。 backend.(*backend).run 那個 100ms 批次計時器——註冊成功、狀態顯示已插樁，hitCount 整整九分鐘都是 0。我換了一行（:452 和 :455 都試過），還是 0。其他十九個點全都有數字。這個函式是 process 啟動時進去、然後就永遠不出來的 goroutine 迴圈，我的猜測是動態插樁只在「函式被呼叫」的那一刻才接得上，所以一個沒有人會再呼叫的函式，永遠走不到那份被插樁的副本。這是我的推測，不是我從裡面驗證過的事實。所以那個 100ms 計時器的節奏，這一輪我沒看到。

pending 不是客戶端寫入數。 它是 bbolt 層排在那個交易裡的操作數。要換算回客戶端寫入要除以 3（而且那個 3 在高負載下會漂——unsafePut 全窗口 11,052 次、客戶端寫入 8,390 筆，比例是 1.32 而不是 3，因為 meta 那幾筆自己也批次化了）。我上面所有寫「幾筆」的地方，講的都是 bbolt 操作。

心跳掉拍那件事，我分不清是誰造成的。 raftNode.tick 在閒置時是每秒 10.0 下，四 client 全速時掉到 5.54 下，讀取相位又回到 10.15 下。方向很清楚——raft 的心跳跟處理 Ready 的迴圈共用同一條路，忙起來就掉拍。但二十個觀測點本身也有成本，這個掉幅有多少是 etcd、有多少是我，我從面板上分不出來。所以我只把它當成一個「值得再查」的訊號，不當結論。

相位邊界有大約 50 筆的歸屬誤差。 面板的命中計數器比伺服器晚一點點，所以在相位交界處，前一段的尾巴會被算進後一段。總數是準的（八個點全部落在 8,390），而且 MVCC 那條 log 帶著 key 前綴，所以每一筆寫入到底屬於哪個相位，逐字查得出來——但每個相位的計數器差值在邊緣是近似的，我沒有拿它去支撐任何比例。

線上面板只裝得下前七分鐘。 整個窗口的資料量超過面板上傳的上限（試過就被回 Invalid string length），所以我把上傳範圍縮到 16:15:08–16:22:09，也就是閒置 + 每秒一筆 + 一 client 全速 + 四 client 的前一半，7 分 1 秒、126,515 筆。上面所有的比例和延遲數字都在這段裡看得到，但線上面板的 ROWS: 7277 對應的是這個子窗口，不是全篇引用的 8,390。

看得到就是看得到，看不到就標明看不到，不給讀者一個假裝完整的東西。

一個對照：etcd 自己的 metrics 為什麼還不夠

這次的對照組特別強：etcd 自己的 Prometheus endpoint 非常完整，而且我整篇的信心有一半是它給的。窗口首尾一減，七組數字全部對上：

etcd 自己的計數器差值我的觀測點命中數

論「數東西」，它比我的觀測點成熟得多。那觀測點多給了什麼？

  1. 它只導出它想導出的東西。 上面那張二十三個腳印的表裡，只有五行有對應的 Prometheus metric。WAL.Save 兩次而 WAL.sync 一次、unsafePut 三次、applyAll 兩次——這些 etcd 一個都不 export。我之所以數得出來，是因為我可以把計數器放在我自己挑的那一行上。
  2. 它是聚合的，不給你逐字現場。 etcd_mvcc_put_total 告訴你寫了幾筆，不告訴你哪一個 key、拿到第幾號修訂。etcd_disk_backend_commit_duration_seconds 給你落盤耗時的直方圖，但不會告訴你那一次落盤攤了幾筆——pending=16 這種東西不存在於任何 metric 裡，因為沒有人事先決定要 export 它。
  3. 它不對帳，是我拿它來對帳我自己。 上面那張表的價值不是「證明 etcd 沒錯」，是證明面板上的數字可以信。有了這個，前面那個十四倍才站得住。

把那把修訂號的尺拿出來驗算一次：整個窗口的 rev 從 2 跑到 8,391，8,391 − 2 + 1 = 8,390，跟面板 log 的 8,390 行、跟客戶端自己數的 8,390 筆一分不差。三個彼此獨立的來源指向同一個數字。

收尾

我沒有改一行 code、沒有重啟 etcd、沒有先埋一套 trace backend。就只是在一個跑著的 process 上挑了二十個位置掛觀測點，然後把負載從「完全不碰」推到「四個 client 全速灌」，再切成只讀不寫，認真看了九分鐘。

換來的是：我看到一個閒置的 etcd 兩分鐘裡心跳 1,200 下、其餘十九個點全是 0；看到一次 put 在十六個位置上留下二十三個腳印，其中 WAL.Save 兩次但只 fsync 一次、bbolt 那層寫了三筆；看到只讀不寫的時候二十個點只有三個會動，但線性化讀取還是要讓 raft 轉一圈；看到負載上來以後只有 bbolt 那一欄脫隊，從 1:1 退到 9.72:1，而 WAL 的 fsync 整整九分鐘只省下 11 次；看到每一次落盤到底攤了幾筆——每秒一筆時永遠是 3，四 client 時最多攤到 16；看到攤 16 筆跟攤 3 筆一樣快，所以 batching 幾乎是白賺的；最後看到那條我完全沒預期的線：同一行 fdatasync，閒的時候 5.9 毫秒，忙的時候 0.4 毫秒。

etcd 是黑盒子，但黑盒子只是「預設看不見」，不是「不能看」。我進去之前對這條路有一套想像，九分鐘之後，那套想像有的被證實、有的被打臉、還有一個位置我根本掛不上去。這三種結果我都寫了，因為它們都是這九分鐘真的發生的事。
